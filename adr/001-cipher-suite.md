# ADR 001 — Cipher Suite: ChaCha20 + BLAKE2s

**Date:** 2026-03-14
**Status:** Accepted

---

## Context

KBVault needs symmetric encryption and a MAC for the encrypt-then-MAC slot
scheme. Standard industry choices would be AES-GCM or AES-CBC + HMAC-SHA256.

The hxcrypt library (which KBVault depends on for all crypto) provides
ChaCha20 and BLAKE2s natively.

## Decision

Use **ChaCha20** for stream encryption and **keyed BLAKE2s** as the MAC,
combined as encrypt-then-MAC.

This is a deliberate personal choice for a personal hacking project. The
reasoning:

- **It's fun.** This is a hobby project, not an enterprise product. Using the
  primitives I find interesting is a feature, not a deviation.
- **Simpler to implement and audit.** ChaCha20 is a pure software cipher with
  no hardware dependency, no block-padding logic, and no key schedule. BLAKE2s
  is similarly straightforward. Both fit in a few hundred lines of C that I
  can read and understand.
- **Still secure.** ChaCha20 and BLAKE2s are standardized, extensively
  analyzed primitives. ChaCha20-Poly1305 is an IETF standard (RFC 8439);
  BLAKE2 is widely deployed (e.g. WireGuard, libsodium). The combination is
  not exotic.
- **No AES acceleration needed.** STM32F401xC has no AES hardware. A software
  AES implementation would be slower and harder to write correctly in
  constant-time than ChaCha20.
- **I use AES and SHA at work.** That's exactly why I don't want them here.

## Consequences

- Cipher suite differs from what auditors/reviewers familiar with AES-GCM
  would expect. If the project ever becomes shared/public, this ADR explains
  the choice.
- No hardware acceleration for ChaCha20 on this MCU either, but ChaCha20 is
  fast enough in software for this use case (5 passwords, infrequent access).
- Nonce is 12 bytes, generated by the CSPRNG per write. Nonce reuse would be
  catastrophic but is extremely unlikely given proper entropy seeding.
